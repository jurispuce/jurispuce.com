# jurispuce.com — repo orientation

A Hugo-built site at **jurispuce.com**. The dominant activity in this repo is **authoring and publishing self-paced courses**; everything else (blog posts, the public-facing pages) is light maintenance by comparison.

## The course pipeline — three layers, three steps

This is the single most important fact about the repo. The pipeline has **three independent persistence layers**, and a complete publish requires touching all three:

| Layer | Lives in | Updated by |
|---|---|---|
| **Lesson content** (HTML + meta) | Supabase Storage (private bucket) | `npm run upload-course -- <slug>` |
| **Catalog card** (the course on `/courses/`) | `content/courses/<slug>.md` (tracked in git) | Regenerated by `upload-course`; **must be committed and pushed** |
| **Access rows** (private courses only) | `public.course_access` Supabase table | `npm run grant-access -- <slug> <email> [<email> ...]` |

Skipping any layer produces a partial deploy. The most common failure: running `upload-course` and stopping — the lessons are in storage but the catalog card never appears on the live site because the regenerated `.md` wasn't committed.

## Where to read more

- **`MANAGING_COURSES.md`** — operational doc. Step-by-step for uploading, granting access, sending emails, public-vs-private. The canonical "how do I do X" source.
- **`.claude/skills/create-course-material/SKILL.md`** — authoring guidance for new lessons. Triggers automatically when the user asks to create or revise a course lesson.
- **`.claude/skills/create-course-material/styling-reference.md`** — design tokens, typography, component patterns. All lessons are self-contained HTML with inline `<style>`; no shared stylesheet.

## Authoring conventions worth knowing up front

- **Course source lives in `course-source/<slug>/`** — gitignored, local-only. Lessons go in `course-source/<slug>/<block-dir>/NN_filename.html` and are registered in `course-source/<slug>/meta.yaml`.
- **`meta.yaml` is the source of truth.** The upload script regenerates `content/courses/<slug>.md` from it on every run. Don't edit the `.md` by hand.
- **Each lesson is a full HTML document** with `<!DOCTYPE html>`, `<meta charset="UTF-8">`, and inline `<style>`. No frameworks. Vanilla JS for interactives.
- **Recurring example organisations** appear across lessons (e.g. Loopwell in `ai-use-case-management-en`, Veridion Dynamics in `risk-management-en`). Stay consistent within a course.

## Common scripts

```bash
npm run upload-course -- <slug>                  # upload lessons + regenerate catalog .md
npm run upload-course -- <slug> --prune          # upload + clean storage orphans
npm run grant-access -- <slug> <email> [<email>] # grant private-course access (idempotent)
npm run send-email -- <slug> <template>          # email enrolled users (welcome, course-update)
```

All scripts require `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `.env`.

## Non-obvious gotchas

- **Private-course access requires the recipient to sign in** at jurispuce.com with the matching email (magic-link or Google OAuth). `grant-access` creates the database row, not the auth user — without a sign-in, the row exists but the card stays hidden.
- **Lessons can't reference external CSS or JS frameworks.** They're rendered standalone in an iframe; only Google Fonts is acceptable as an external dependency.
- **Hugo deploy is via git push** (assume Netlify/Cloudflare/equivalent pulling from main). The storage upload alone never publishes the catalog — the commit does.
