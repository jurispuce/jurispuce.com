# Managing Courses

Course HTML files are stored in **Supabase Storage** (private bucket), not in git.
The Hugo site only contains auto-generated catalog pages (`content/courses/<slug>.md`).

## Prerequisites

```bash
npm install
cp .env.example .env   # fill in SUPABASE_SERVICE_ROLE_KEY (and Gmail creds for emails)
```

Required `.env` variables for course upload:
- `SUPABASE_URL` — Supabase project URL
- `SUPABASE_SERVICE_ROLE_KEY` — service role key (from Supabase dashboard)
- `SUPABASE_COURSE_BUCKET` — bucket name (default: `course-materials`)

Additional variables for email sending:
- `GMAIL_USER` — Gmail address
- `GMAIL_APP_PASSWORD` — Gmail App Password ([generate here](https://myaccount.google.com/apppasswords))
- `EMAIL_FROM` — sender display name and address

## Directory structure

```
course-source/              # gitignored — local only
  <slug>/
    meta.yaml               # source of truth for file list and course metadata
    lesson-01.html           # full HTML documents (must include <meta charset="UTF-8">)
    lesson-02.html
    ...

content/courses/
  <slug>.md                  # auto-generated by upload script — do not edit by hand

scripts/
  upload-course.js           # uploads files + regenerates catalog
  send-course-email.js       # sends emails to course participants
  meta.example.yaml          # template for new meta.yaml files

email-templates/
  welcome.html               # English welcome email
  welcome-lv.html            # Latvian welcome email
  course-update.html         # new materials notification
```

## Uploading / updating course content

1. Edit or add HTML files in `course-source/<slug>/`
2. Update `course-source/<slug>/meta.yaml` if files were added/removed or metadata changed
3. Run the upload:

```bash
npm run upload-course -- <slug>
```

This will:
- Upload all files listed in `meta.yaml` to Supabase Storage (upserts — safe to re-run)
- Regenerate `content/courses/<slug>.md` from `meta.yaml`

4. Commit and push the regenerated `.md` file:

```bash
git add content/courses/<slug>.md
git commit -m "Update <slug> course catalog"
git push
```

### Important notes

- HTML files must be **full documents** with `<!DOCTYPE html>`, `<meta charset="UTF-8">`, etc.
  Fragments without charset will display broken Latvian characters (mojibake).
- `meta.yaml` is the single source of truth — the upload script regenerates the catalog `.md` from it.
  Manual edits to the `.md` file will be overwritten on the next upload.
- Re-running the upload is safe — files are upserted (overwritten, not duplicated).

## Sending emails to participants

Available templates: `welcome`, `welcome-lv`, `course-update`

```bash
# Preview without sending
npm run send-email -- <slug> <template> --dry-run

# Send to a single address (for testing)
npm run send-email -- <slug> <template> --to your@email.com

# Send to all course participants
npm run send-email -- <slug> <template>
```

### Targeting a subset of participants

By default the script emails **every** enrolled user for the slug. To target a
subset (e.g. people you just added), use one of:

- `--to a@x.com,b@y.com` — comma-separated explicit list. Replaces the
  Supabase-derived list. Addresses not enrolled get a warning but are still
  sent to.
- `--emails-file <path>` — newline-delimited file of addresses. Blank lines and
  lines starting with `#` are ignored. Combine with `--to` to union the two.
- `--since <ISO-date>` — only enrolled users whose `granted_at >= <date>`.
  Useful right after a bulk insert into `public.course_access`. Ignored if
  `--to` or `--emails-file` is also set.

### Examples

```bash
npm run send-email -- is-auditor welcome-lv --dry-run
npm run send-email -- is-auditor welcome-lv --to test@example.com
npm run send-email -- is-auditor welcome --to a@example.com,b@example.com --dry-run
npm run send-email -- is-auditor welcome --emails-file ./batch.txt --dry-run
npm run send-email -- is-auditor welcome --since 2026-05-01 --dry-run
npm run send-email -- is-auditor course-update
```

## Adding a new course

1. Create `course-source/<new-slug>/` directory
2. Copy `scripts/meta.example.yaml` to `course-source/<new-slug>/meta.yaml` and fill it in
3. Decide visibility — set `private: true` in `meta.yaml` if the course should only show in the catalog for users on its allowlist (see below). Default is public.
4. Add HTML lesson files to the directory
5. Run `npm run upload-course -- <new-slug>`
6. Commit the generated `content/courses/<new-slug>.md`

## Public vs private courses

By default, courses appear in `/courses/` for every visitor. Set `private: true` in `meta.yaml` to hide a course from the public catalog — it will only render for signed-in users with a matching `(email, course_slug)` row in `public.course_access`.

File access (the lessons themselves) is always gated by storage RLS regardless of `private` — the flag only controls catalog discovery.

### Granting access to a private course

Use the `grant-access` script. It upserts `(email, course_slug)` rows into `public.course_access`; idempotent and safe to re-run.

```bash
npm run grant-access -- <slug> alice@example.com bob@example.com
```

Emails are lowercased before insertion. Requires `SUPABASE_URL` and `SUPABASE_SERVICE_ROLE_KEY` in `.env` (same as the upload and email scripts).

The recipient must subsequently sign in at `jurispuce.com` with the matching email — the site uses magic-link (OTP) or Google OAuth. Granting access creates the database row, not the auth user — without the sign-in step, the card stays hidden even though access is granted.

If you prefer the manual route, you can still add rows directly via Supabase dashboard → Table Editor → `public.course_access`.

## Publishing changes — the three-way split

The course pipeline has three independent persistence layers. After authoring or updating content, **all three** may need a step:

| Layer | Lives in | Updated by | Visible when |
|---|---|---|---|
| **Lesson content** (HTML + meta) | Supabase Storage (private bucket) | `npm run upload-course -- <slug>` | Immediately after upload (fetched by signed URL at view time) |
| **Catalog card** (course on `/courses/`) | `content/courses/<slug>.md` (tracked in git) | Regenerated by `upload-course`; **must be committed and pushed** | After git push → Hugo build → deploy |
| **Access rows** (private courses only) | `public.course_access` table | `npm run grant-access -- <slug> <email>` | Immediately after insert, but requires recipient to sign in with the matching email |

A common failure mode: running `upload-course`, granting access, and stopping. The lessons are uploaded and accessible *by URL*, but the catalog card never appears on the live site because the regenerated `.md` was not committed. Always finish with:

```bash
git add content/courses/<slug>.md
git commit -m "Update <slug> course catalog"
git push
```

For private courses, also run the grant-access step before announcing the course.
